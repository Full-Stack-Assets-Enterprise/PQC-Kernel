# Next Evidence and Commercial Gates

Version 0.1 is approved for controlled proof work, not production assurance or a
compliance claim.

## Gate 1 — Real-project falsification

Run the source detector against pinned revisions of two C/C++ projects and one
customer-approved binary set. Hand-label every emitted finding and a sampled set
of non-findings. Record precision only for the supported lexical/API scope; do
not publish recall without a defensible ground truth.

Exit evidence:

- Pinned source revision and build commands.
- Analyst-labeled finding register.
- False-positive causes and detector-rule changes.
- Coverage-gap inventory.
- Reproducible scan bundles and externally retained integrity receipts.

## Gate 2 — Assessment dossier proof

Use one approved target to complete a human-edited assessment dossier. Validate
whether a security architect can trace each executive statement to an atomic
observation and can distinguish evidence, inference, limitation, and policy.

Exit evidence:

- Reviewed dossier and redacted exemplar.
- Customer data-handling signoff.
- Evidence-to-finding traceability review.
- Documented analyst hours and delivery effort.

## Gate 3 — Paid wedge

Sell a bounded Linux x86-64 C/C++ assessment with the exclusions in `SCOPE.md`.
Do not promise Java/Windows/firmware, runtime proof, static-link recovery,
stripped-binary fingerprinting, automatic patches, or final FAR compliance.

Exit evidence:

- Signed scope and data-handling terms.
- Paid engagement or deposit.
- Named customer decision owner.
- Delivery acceptance criteria.

## Gate 4 — Architecture expansion

Only after customer evidence, choose the smallest justified expansion:

1. Clang AST support if macros/type resolution cause material misses.
2. Mechanism/provider resolution if EVP/PKCS#11 unknowns dominate analyst time.
3. CycloneDX/SARIF projections if a buyer names them as acceptance criteria.
4. Signed receipts if customer evidence custody requires authenticity.
5. SQLite/protobuf or Rust only if measured volume, distribution, or integration
   requirements exceed the Python/JSONL design.

eBPF, NTT constant detection, multi-tenancy, a web UI, Helm/OIDC, public
leaderboards, issue-tracker writes, and automatic remediation remain outside the
commercial v0.1 boundary.
